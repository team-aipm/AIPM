## 1. 적용 대상

**정함 · COM-002 §3·§4**

이 서비스에는 사람이 둘 있고, 둘의 지위가 다르다.

```text
Account    부모       회원. 계약 · 결제 · 동의의 주체
Student    학생       부모 계정 안의 프로필. 별도 계정이 아니다
```

학생은 **초등 4~6학년(만 9~12세)** 이므로 전원 **만 14세 미만**이다
(COM-002 §4 `grade` CHECK 4~6). 따라서 학생 개인정보의 처리 근거는 **법정
대리인(부모)의 동의**다. 학생이 스스로 가입하거나 동의하는 경로를 만들지
않는다.

**이 구조는 이미 코드에 반영돼 있다.**

- `account.account_id` = `auth.users.id` — 로그인하는 사람은 부모뿐이다.
- `student` 는 `account_id` 를 가진 행이며 로그인 수단이 없다.
- 학생 화면(`(student)`)도 부모 계정의 세션으로 연다.

> **보류 — 법률 검토.** 만 14세 미만 법정대리인 동의의 **확인 방법**(본인
> 확인 수준, 동의 이력 보관 형식)은 국내 개인정보 보호법 해석이 필요하다.
> 이 문서는 "부모 계정이 동의 주체" 까지만 정한다. 출시 전 외부 검토를
> 받는다.

## 2. 수집 항목과 근거

### 2-1. 부모 (COM-002 §3) · **정함**

| 항목 | 필수 | 목적 |
|---|---|---|
| `account_name` | 필수 | 계약 주체 확인 · CS 응대 |
| `email` | 필수 | 로그인 ID · 계정 복구 · 결제 안내 |
| `phone_number` | 필수 | 본인 확인 · 결제 실패 안내 |
| `birth_date` | 필수 | 성인 여부 확인(법정대리인 자격) |
| `marketing_*_opt_in` | **선택** | 소식 발송. 3종 각각 별도 동의 |

마케팅 3종은 선택이며, 동의하지 않아도 서비스 이용에 제한이 없다. 가입
화면(AUTH-002)에서 기본값은 꺼짐이다.

### 2-2. 학생 (COM-002 §4) · **정함**

| 항목 | 필수 | 목적 |
|---|---|---|
| `student_name` | 필수 | 부모가 자녀를 구분 |
| `nickname` | 필수 | AI 가 부르는 이름. 기본값은 `student_name` |
| `birth_date` | 필수 | 연령 적합성 확인 |
| `grade` | 필수 | 문제 난이도 · 학년 적합성 (COM-001 §9) |
| `login_id` | 선택 | 아이가 자기 기기에서 로그인 (2026-09-10 추가) |
| `auth_user_id` | 선택 | 위 계정의 Auth 식별자 |

### 2-2-1. 아이 로그인을 만들 때 무엇이 늘어나는가 · **이번에 정함**

**늘어나는 것은 아이디 하나뿐이다.** 이메일 주소도 전화번호도 받지 않는다.

`login_id`는 부모가 짓는다. 아이 본인이 스스로 가입하지 않는다 — 만 14세
미만의 가입에는 법정대리인 동의가 필요하기 때문이다(§1).

Supabase Auth 는 이메일로만 로그인하므로, 서버가 아이디를 가짜 이메일
(`<login_id>@student.aipm.invalid`)로 바꿔 넘긴다. `.invalid` 는 RFC 2606 이
예약한 TLD 라 **실제로 등록될 수 없고, 메일이 오갈 수 없다.** 그래서
아이에게 어떤 형태로도 연락 수단을 갖지 않는다.

- 아이디를 **실명이나 생년월일로 짓지 말라고 화면에서 권하지 않는다** —
  권해도 지키기 어렵고, 아이디는 부모와 아이 둘만 보는 값이다. 대신 로그인
  화면은 아이디의 존재 여부를 알려주지 않는다(맞지 않을 때 같은 문구).
- 비밀번호는 부모가 정하고 부모가 바꾼다(MY-003). 메일로 찾는 길은 없다.
- 아이 계정으로는 부모 화면(결제 · 리포트 · 상세 평가)에 갈 수 없다.
  RLS 가 `account` · `subscription` · `payment` 행을 주지 않는다.
- 아이 계정으로 바꿀 수 있는 것은 파트너(`persona_type`) 하나다.
  DB 트리거가 나머지를 막는다(COM-002 §4-1).

### 2-3. 학생 생년월일을 꼭 받아야 하는가 · **이번에 정함**

**받는다. 다만 쓰는 곳을 학년 확인 하나로 제한한다.**

학습에 실제로 쓰이는 값은 `grade` 다. 생년월일은 **입력한 학년이 나이와
맞는지 확인**하는 데만 쓴다 — 만 14세 미만 서비스인데 중학생이 등록되는 것을
막기 위해서다.

- 생일 프로모션 등 **마케팅 목적으로 학생 생년월일을 쓰지 않는다**(§9).
- AI 에게 보내지 않는다(§6).
- 부모 화면에도 표시하지 않는다. 수정은 학생 정보 화면에서만 한다.

## 3. 생성 데이터

학생이 서비스를 쓰면서 만들어지는 데이터다. 수집한 것이 아니라 **생기는**
것이라, 따로 다룬다.

| 데이터 | 테이블 · 저장소 | 성격 |
|---|---|---|
| AI 대화 원문 | `message` | 학습기록 |
| 문제 사진 | Supabase Storage | **학습 자료** (아래 3-1) |
| 문제 · 평가 · Logic Gap | `problem` · `evaluation` · `logic_gap` | 학습기록 |
| Student Memory | `student_memory` | 학습기록 |
| 행동 이벤트 | `event` | 서비스 분석 |

### 3-1. 문제 사진의 성격 · **이번에 정함**

**문제 사진은 아동의 개인정보가 아니라 학습 자료로 분류한다.**

찍히는 것은 교재나 공책에 있는 **문제**이지 아이 자신이 아니다. 얼굴 ·
주소 · 연락처 같은 식별 정보를 담기 위해 찍는 것이 아니며, 담겨서도 안 된다.
따라서 사진 자체를 아동 개인정보로 보아 별도의 동의 · 파기 절차를 두지
않는다.

**다만 세 가지 규칙을 함께 둔다.** 사진은 아이가 찍는 것이라, 의도치 않게
다른 것이 함께 찍힐 수 있다.

1. **얼굴이나 이름이 함께 찍힌 사진은 그대로 두지 않는다.** 학생 화면에
   "문제만 나오게 찍어줘" 를 안내하고, 인식(00 OCR) 결과에서 문제 텍스트만
   남긴다.
2. **사진은 문제 인식이 끝나면 오래 두지 않는다**(§4-3). 학습기록에 남는
   것은 인식된 **문제 텍스트**이지 사진이 아니다.
3. **운영자는 사진을 기본으로 열람하지 못한다**(§7).

> 이 분류는 서비스 운영상의 판단이다. 사진에 식별 정보가 반복해서 담기는
> 것이 확인되면 분류를 다시 본다.

## 4. 보관 기간

### 4-1. 학습기록 · **정함 (COM-002 §18)**

```text
학생 삭제 요청           student_status = deleted_pending · deleted_at 기록
                        learning_data_retain_until = deleted_at + 1년
1년 경과                 완전 삭제
```

### 4-2. 1년 경과 후 — 삭제인가 익명화인가 · **이번에 정함**

**완전 삭제한다.**

익명화는 "지웠다" 고 말하기 어렵다. 학습기록은 대화 원문 · 문제 · 평가가
서로 이어져 있어서, 식별자만 떼어내도 대화 내용으로 누구인지 좁혀지는 일을
막기 어렵다. 통계가 필요하면 **집계값을 미리 따로 쌓는다**(`event` ·
`learning_report`) — 원본을 남겨 두는 대신이다.

삭제 대상: `student` 및 그에 딸린 `learning_session` · `problem` ·
`message` · `evaluation` · `logic_gap` · `student_memory`. FK 가
`on delete cascade` 이므로 `student` 행을 지우면 함께 지워진다.

### 4-3. 문제 사진 · **이번에 정함 (COM-005 §9 위임분)**

```text
인식 성공     문제 텍스트를 problem.problem_text 에 남기고
              사진은 30일 뒤 삭제
인식 실패     즉시 삭제. 남길 이유가 없다
학생 삭제     즉시 삭제 (1년 유예를 적용하지 않는다)
```

30일을 두는 이유는 하나다 — **인식이 잘못됐다는 신고가 들어왔을 때 원본을
봐야 하기 때문**이다. 그 기간이 지나면 사진의 쓸모는 없고 보관 비용과
위험만 남는다.

지우는 일은 배치가 한다 — `GET /api/batch/photo-sweep`, 매일 03:00(KST).
`CRON_SECRET` 을 아는 요청만 받는다. **만든 시각을 모르는 파일은 지우지
않는다** — 지우는 쪽이 되돌릴 수 없다.

### 4-4. AI 대화 원문 · **이번에 정함**

학습기록과 같이 다룬다(§4-1). 대화가 곧 학습 과정이라 따로 떼어 지울 수
없다 — 대화를 지우면 평가의 근거가 사라진다.

### 4-5. 결제 데이터 · **정함**

전자상거래법이 정한 기간을 따른다. 학생 삭제나 회원탈퇴와 무관하게 남는다.

| 항목 | 기간 |
|---|---|
| 대금 결제 · 재화 공급 기록 | 5년 |
| 소비자 불만 · 분쟁 처리 기록 | 3년 |

탈퇴 화면(MY-009)에 **"결제 기록은 법에 따라 남습니다"** 를 표시한다.

## 5. 삭제

### 5-1. 학생 프로필 삭제 (MY-003) · **이번에 정함**

```text
1  부모가 학생 삭제를 요청
2  student_status = deleted_pending · deleted_at = now
   learning_data_retain_until = now + 1년
3  30일 안에는 부모가 되돌릴 수 있다
4  30일 경과 → 되돌릴 수 없다. 화면에서 완전히 사라진다
5  1년 경과 → 배치가 행을 지운다 (§4-2)
```

**되돌릴 수 있는 기간을 30일로 둔다.** 아이가 여럿인 계정에서 실수로 다른
아이를 지우는 일이 실제로 생기고, 학습기록은 다시 만들 수 없다.

### 5-2. 회원탈퇴 (MY-008 → MY-009 → MY-010) · **이번에 정함**

계정을 지우면 **그 계정의 모든 학생이 함께 삭제 절차에 들어간다.** 학생만
지우는 것과 다른 점은 로그인 수단(`auth.users`)이 함께 사라진다는 것이다.

```text
학생 1명 삭제    그 학생만. 계정과 다른 학생은 그대로
회원탈퇴        계정 + 모든 학생 + 로그인 수단
                결제 기록은 법정 기간 동안 남는다(§4-5)
```

탈퇴 후 30일 안에는 같은 이메일로 복구를 요청할 수 있다. 30일이 지나면
같은 이메일로 **새로 가입**하는 것이며 이전 기록은 이어지지 않는다.

### 5-3. 구현 메모

삭제 배치는 `service_role` 로 도는 서버 작업이다(§10). 아직 만들지 않았다 —
`deleted_pending` 인 학생이 생기기 시작하면 그때 만든다.

## 6. AI Provider 전달 범위

### 6-1. 지금 실제로 보내는 것 · **정함 (코드 기준)**

`src/app/(student)/mission/_actions.ts` 가 만드는 입력이 전부다.

```text
student.student_id       UUID. 이름이 아니다
student.grade            학년
student.selected_persona FRIEND · VILLAIN
session.session_id       UUID
session.problem_number   오늘 몇 번째 문제인지
conversation             AI 와 학생이 주고받은 말
payload.problem          문제 · 검증된 정답
```

### 6-2. 실명 · 닉네임을 보내는가 · **이번에 정함**

**보내지 않는다.** 지금 코드도 보내지 않는다.

AI 가 아이를 이름으로 부르면 더 친근하겠지만, 그 대가로 **외부 API 요청마다
아이 이름이 실린다.** 친근함은 말투(Persona)로 만들 수 있고, 그것이 이
서비스가 이미 고른 방법이다(COM-001 §19).

생년월일도 보내지 않는다. 학년만으로 충분하다.

### 6-3. 문제 사진 원본을 보내는가 · **이번에 정함**

**보낸다.** 사진에서 문제를 읽어내는 일(00 OCR)은 모델이 하는 것이므로 원본
없이는 성립하지 않는다. 대신 §3-1 의 세 규칙으로 범위를 좁힌다.

### 6-4. Provider 의 학습 데이터 사용 · **정함 (약관 확인 완료 · 등급 확인 필요)**

`ai.google.dev/gemini-api/terms` 를 2026-09-10 에 확인했다. **등급에 따라
완전히 다르다.**

| | 유료(paid) | 무료(unpaid) |
|---|---|---|
| 모델 학습 사용 | **안 함** | **함** — 제품 개선·머신러닝에 사용 |
| 사람의 열람 | 없음 | **있음** — 검토자가 읽고 주석을 달 수 있음 |
| 보관 | 남용 탐지 목적 30일 | 명시적 제한 없음 |

원문: *"Google doesn't use your prompts (including associated system
instructions, cached content, and files such as images, videos, or documents)
or responses to improve our products"* (유료) / *"human reviewers may read,
annotate, and process your API input and output"* (무료)

**따라서 이 서비스는 유료 등급에서만 운영한다.**

- 무료 등급 키로 운영하면 **아이의 대화와 사진이 학습 데이터가 되고 사람이
  읽을 수 있다.** 사진을 학습 자료로 분류한 §3-1 의 판단과는 별개의 문제다 —
  대화에는 아이가 어떻게 생각하는지가 그대로 들어 있다.
- 결제가 꺼진 프로젝트로 전환되면 **약관이 바뀐 것과 같다.** 키를 바꿀 때
  등급을 함께 확인한다.

> **확인 필요 — 운영.** 지금 `.env.local` 의 `GEMINI_API_KEY` 가 결제가
> 켜진 프로젝트의 키인지 확인해야 한다. 코드로는 알 수 없다.

## 7. 열람 권한 — ADM 영역의 선행 조건

### 7-1. 원칙 · **이번에 정함**

**운영자는 기본적으로 아동의 학습 내용을 볼 수 없다.** 필요할 때, 필요한
만큼, 흔적을 남기고 본다.

| 대상 | 기본 | 열람 조건 |
|---|---|---|
| AI 대화 원문 | **불가** | 부모의 CS 요청이 있고, 그 요청에 연결된 건만 |
| 문제 사진 | **불가** | 인식 오류 신고 건만. 30일 안에만 존재(§4-3) |
| 학습기록 · 평가 · Logic Gap | **집계만** | 개별 문제 내용은 위와 같은 조건 |
| 학생 이름 · 생년월일 | **마스킹** | 해제하려면 사유 입력 |
| 부모 이름 · 이메일 · 연락처 | **마스킹** | 해제하려면 사유 입력 |

어드민 와이어프레임(2026-09-03)이 이미 이 방향으로 그려져 있다 — 목록에서
`김**` · `ki**@gmail.com` 으로 가리고, "마스킹 해제하면 감사 로그가
남는다" 고 적혀 있다.

### 7-2. 권한 등급 · **이번에 정함**

```text
전체        모든 조회 + 데이터 변경. 마스킹 해제 가능
CS          CS 문의에 연결된 건만 조회. 마스킹 해제 가능(사유 필수)
읽기전용     집계 화면만. 마스킹 해제 불가
```

### 7-3. 감사 로그 · **이번에 정함**

**마스킹 해제와 대화 원문 열람은 반드시 기록한다.** 누가 · 언제 · 무엇을 ·
왜 봤는지가 남지 않으면 위의 규칙은 글일 뿐이다.

> **COM-002 변경 필요.** `AuditLog` 와 `AdminUser` 엔티티가 없다. ADM 화면을
> 만들기 전에 COM-002 에 추가해야 한다(§13 참조).

## 8. 부모의 열람 범위 · **이번에 정함**

**부모는 자녀의 AI 대화 원문을 볼 수 있다.** 계정 주체이자 법정대리인이고,
아이가 무엇을 배웠는지 확인하는 것이 이 서비스를 쓰는 이유다.

다만 **학생 화면의 규칙과 혼동하지 않는다.**

```text
학생 화면    상세 평가점수 · Logic Gap 노출 안 함 (COM-003)
부모 화면    사고능력 · 자주 막힌 부분으로 볼 수 있음 (copy.ts)
```

부모는 **읽을 수만 있다.** 난이도 · Logic Gap · Student Memory 를 고치지
못한다(COM-003 §9). 학습 판단을 사람이 손대면 다음 문제 선정이 어긋난다.

---

## 9. 마케팅 수신동의 · **이번에 정함**

- 대상은 **부모뿐**이다. 학생에게는 어떤 마케팅도 보내지 않는다.
- 이메일 · SMS · 알림톡 3종을 **각각** 받는다(COM-002 §3). 한 번에 묶지
  않는다.
- 철회는 마이페이지(MY-006)에서 언제든 가능하며, 철회 즉시 발송을 멈춘다.
- **생일 프로모션에 학생 생년월일을 쓰지 않는다**(§2-3). 필요하면 부모
  생년월일을 쓴다.

## 10. RLS 정책 · **정함 (구현 완료)**

`supabase/migrations/20260831090200_enable_rls_policies.sql` 에 이미 있다.

```text
account            account_id = auth.uid()
student            account_id = auth.uid()
학습 데이터 전체     owns_student(student_id)
                   learning_session · problem · message
                   evaluation · logic_gap · student_memory
subscription       조회만
payment            조회만
learning_report    조회만
event              본인 계정 또는 본인 학생
```

- **RLS 없는 테이블은 만들지 않는다**(DEV-003 §4-5).
- `service_role` 은 **서버 배치에만** 쓴다. 사용자 요청을 처리하는 경로에서
  쓰지 않는다 — RLS 를 통째로 건너뛰기 때문이다. 지금 쓰는 곳은 없다.
- 삭제 정책은 두지 않는다. 삭제는 `student_status` 로 처리하고(§5-1), 실제
  행 삭제는 배치만 한다.

## 11. 약관 · 동의 화면 (AUTH-003) · **이번에 정함**

가입할 때 받는 동의다. **필수와 선택을 화면에서 분명히 나눈다.**

| 구분 | 항목 |
|---|---|
| 필수 | 서비스 이용약관 |
| 필수 | 개인정보 수집·이용 동의 (부모) |
| 필수 | **만 14세 미만 자녀의 개인정보 처리에 대한 법정대리인 동의** |
| 선택 | 마케팅 수신 (이메일 · SMS · 알림톡 각각) |

- 필수 항목에 모두 동의해야 가입이 진행된다.
- **동의 이력을 남긴다** — 무엇에, 언제, 어떤 버전의 약관에 동의했는지.

> **COM-002 변경 필요.** 동의 이력을 담을 자리가 없다. `account` 에 컬럼을
> 더할지 별도 테이블을 둘지 정해야 한다. 약관은 개정되므로 **버전**이 함께
> 남아야 한다(§13).

> **보류 — 약관 본문.** 위는 구성이고, 문구 자체는 법률 검토가 필요하다.
