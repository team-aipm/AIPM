# COM-003 · 화면 목록 및 공통 UI 정의서 --- 개발용

> **Version:** 1.0 · **Updated:** 2026-08-28 · **Owner:** (미지정)\
> **Status:** 확정\
> **Changelog:** 문서 최하단 참조

> **문서 역할:** Claude Code 및 5개 PM이 공통으로 참조하는 화면
> 구조·화면 ID·State/Modal·공통 UI의 Source of Truth\
> **기준 문서:** `COM-001-service-flow.md`, `COM-002-data-model.md`\
> **MVP 기준:** 모바일 우선 / 초등학교 4\~6학년 수학 / 학생 미션 경험 +
> 보호자 관리 경험\
> **중요:** `AUTH`, `STU`, `MIS` 등은 화면이 아니라 **Area(화면
> 묶음)**이다. 실제 화면은 `AUTH-001`, `STU-004`처럼 Screen ID를 가진다.

## 1. 문서 목적

-   서비스 전체 화면을 Area별로 정의
-   실제 독립 Screen과 Screen 내부 State/Modal 구분
-   5개 PM이 동일한 Screen ID와 화면명 사용
-   학생 영역과 보호자 영역의 UI 원칙 구분
-   COM-001 서비스 흐름과 COM-002 데이터 구조를 실제 UI로 연결

## 2. UI 구조 기본 원칙

`Area → Screen → State / Modal → Common Component`

-   **Area:** 기능적으로 연관된 화면의 상위 묶음
-   **Screen:** 고유 Screen ID를 가진 실제 화면 단위
-   **State:** 동일 Screen 안에서 상황에 따라 달라지는 상태
-   **Modal:** 사용자의 확인·선택이 필요한 임시 UI
-   State/Modal은 불필요하게 별도 Route로 만들지 않음

## 3. Area 목록

  Area ID   Area명      역할                                   주요 사용자
  --------- ----------- -------------------------------------- -------------
  `AUTH`    회원·인증   가입, 로그인, 인증, 계정 접근          부모
  `STU`     학생        학생 등록·선택, 학생 HOME, Persona     학생/부모
  `MIS`     미션        문제, AI 대화, 문제 출제, Drill-down   학생
  `PAR`     보호자      보호자 인증 및 부모 HOME               부모
  `RPT`     리포트      학생의 성장 결과 및 상세 데이터 확인   부모
  `BIL`     구독·결제   무료체험, 학생별 구독, 결제 관리       부모
  `MY`      마이·설정   학생·회원정보 및 각종 설정             부모

> `SYS`는 Area로 사용하지 않는다. AI 오류, 네트워크 오류, Loading 등은
> 여러 Screen에서 재사용하는 공통 State/Component로 관리한다.

**AUTH-001 은 칸이 하나다** (2026-09-10). `@` 가 있으면 부모의 이메일,
없으면 아이의 아이디로 본다. 「보호자용」/「학생용」을 고르게 하지 않는다 —
아이가 고르는 것부터 틀린다. 들어간 뒤 부모는 `STU-002`(학생 선택)로,
아이는 자기 홈으로 간다. 새 Screen ID 를 만들지 않는다.

아이 계정은 부모가 `MY-003`에서 만들어 준다. `AUTH-002`(회원가입)는 부모
전용이며 그대로다 — 아이는 스스로 가입하지 않는다(COM-007 §2-2-1).

변경 - 학생 바꾸기

상태별 Primary Action: - 최초: `첫 미션 시작하기` - 오늘 시작 전:
`오늘의 미션 시작하기` - 진행 중: `미션 이어하기` - 10개 완료:
`오늘의 기록 보기`

학생에게 직접 노출하지 않음 - 정답 보기 버튼 없음 - AI 응답 중 중복 전송
방지 - 저장 버튼 없음. 대화 턴 단위 자동 저장

사진 문제 흐름:
`MIS-002 → 사진 촬영 → MIS-003 → 문제 인식 → 학생 확인/수정 → 정답 검증 → Answer Lock → MIS-001`

학생 확인 전 학습을 시작하지 않으며 검증 실패 시 추측하여 진행하지
않는다.

  Area     Screen ID   화면명             사용자   주요 목적
  -------- ----------- ------------------ -------- -----------------------
  리포트   `RPT-001`   주간 성장 리포트   부모     학생의 주간 성장 요약
  리포트   `RPT-002`   리포트 상세        부모     상세 학습 데이터 확인
  리포트   `RPT-003`   지난 리포트        부모     과거 주간 리포트 조회

주간 성장 리포트 순서: 1. 이번 주 한눈에 보기 2. 이번 주 가장 성장한
능력 3. 사고능력 변화 4. 자주 막힌 부분 5. 다음 주 방향 6. 자세히 보기

내부 데이터 → 부모 표현: - `reasoning_score` → 이유 설명하기 -
`self_correction` → 스스로 바로잡기 - `rule_score` → 규칙 찾아내기 -
`transfer_score` → 새로운 문제에 적용하기 - `support_level` → 도움 없이
해결하기 - `logic_gap` → 자주 막힌 부분

기본 화면은 성장 이야기 중심, 상세 화면은 데이터 중심으로 구성한다.

## 7. 학생 영역 공통 UI 원칙

학생 화면에서는 `학습` 표현을 최소화하고 다음 용어를 우선 사용한다.

  내부/기존 표현   학생 UI
  ---------------- ---------------
  학습             미션 / 도전
  학습 시작        미션 시작하기
  이어서 학습      미션 이어하기
  학습 결과        오늘의 기록
  다음 문제        다음 미션
  추가 학습 필요   한 번 더 도전

-   부모 영역과 내부 시스템에서는 `학습`, `평가`, `리포트`,
    `LearningSession`, `Evaluation`, `LogicGap` 등 정확한 용어 유지
-   한 화면에서 Primary Action은 1개만 강조
-   학생에게 상세 평가점수 직접 노출 금지
-   정답률보다 참여·성장·사고행동 중심
-   불필요한 Popup 최소화
-   오류를 학생의 잘못처럼 표현하지 않음

오류 문구 예: - `문제를 잘 읽지 못했어. 다시 한번 보여줄래?` -
`잠깐 문제가 생겼어. 다시 해볼까?`

## 8. Persona UI 원칙

-   Persona는 학생이 직접 선택
-   설정이 아니라 `함께할 캐릭터 선택` 경험으로 제공
-   내부 값: `friend`, `villain`
-   실제 캐릭터 이름·외형은 디자인 단계에서 확정
-   변경은 다음 미션부터 적용
-   Persona는 말투/연출만 변경
-   정답, 평가, 난이도, 검증 로직에는 영향 없음
-   부모는 현재 Persona를 확인할 수 있으나 통제 기능은 MVP에서 제공하지
    않음

## 9. 부모 영역 공통 UI 원칙

-   정보 확인·관리 중심
-   부모가 이해하기 쉬운 표현 사용
-   상세 데이터는 `자세히 보기`에서 제공
-   학생별 무료체험/구독 상태 명확히 구분
-   결제·회원정보·마케팅 설정은 부모 영역에서 제공
-   학생의 난이도, Logic Gap, Student Memory는 부모가 직접 수정할 수
    없음

## 10. Device 원칙

-   모바일 우선 설계
-   문제 사진 촬영과 학생 접근성을 우선 고려
-   태블릿/PC는 동일 정보구조를 Responsive하게 확장
-   기기별로 기능 의미가 달라지지 않도록 함

## 11. Navigation 원칙

학생: - 고정 하단 Navigation 없음 - 학생 HOME에서 오늘의 미션, 내가 문제
내기, Persona, 학생 바꾸기, 보호자 메뉴 제공

부모: - 고정 하단 Navigation: `[홈] [리포트] [구독] [마이]` - 학생 ↔ 부모
이동에 별도 확인 절차를 두지 않는다

## 13. Claude Code 구현 규칙

1.  Screen ID와 화면명을 임의 변경하지 않는다.
2.  Area를 Screen으로 구현하지 않는다.
3.  State/Modal을 불필요하게 별도 Route로 만들지 않는다.
4.  공통 오류·Loading UI는 재사용 Component로 만든다.
5.  학생 UI와 부모 UI의 용어 정책을 구분한다.
6.  학생 영역에서 `학습`, 평가점수, Logic Gap 같은 내부 표현을 직접
    노출하지 않는다.
7.  `COM-002-data-model.md`의 필드명과 상태값을 임의 변경하지 않는다.
8.  화면 추가 전 기존 Screen의 State/Modal로 해결 가능한지 확인한다.
9.  새로운 Screen이 반드시 필요하면 COM-003 변경 필요사항을 먼저
    제시한다.
10. 모바일 우선으로 구현하고 Responsive하게 확장한다.
