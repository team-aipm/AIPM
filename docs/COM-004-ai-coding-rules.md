## 1. 문서 우선 원칙

### 1-1. 문서와 코드가 다르면

**코드를 고치지 않고 먼저 보고한다.** 문서가 틀렸다고 판단해도 마찬가지다.
고치고 나서 알리면, 그 결정이 누구의 것이었는지가 커밋 로그에만 남는다.

```text
1  무엇이 어긋나는지 그대로 말한다 (문서 § · 코드 파일)
2  고치는 안을 낸다
3  승인 뒤에 고친다
```

### 1-2. 작업 전 확인 순서

| 작업 | 문서 |
|---|---|
| 무엇이든 | `docs/README.md` |
| 화면 | `COM-003` → `DEV-002` (Screen ID 와 Route) |
| DB · 필드 | `COM-002` |
| 학습 로직 · 상태 전이 | `COM-001` |
| 파일 위치 | `DEV-001` |
| 스택 · 환경변수 | `COM-005` |
| 개인정보 · 사진 · 삭제 | `COM-007` |

### 1-3. 문서 → DB → 코드 순서의 예외

**없다.** 필드가 없으면 COM-002 변경을 먼저 제안한다(§8-2). 이 순서를
어긴 사례가 실제로 사고를 냈다 — `auth.users` 트리거가 원격 DB 에만
적용돼 있고 저장소에는 초안으로만 있어서, 대시보드에서 계정을 만들 수
없는데 이유를 코드에서 찾을 수 없었다(2026-09-09).

## 2. 작업 단위

### 2-1. 한 번에 다루는 범위

**화면 1개 또는 기능 1개.** Area 전체를 한 번에 하지 않는다.

기준은 "이 PR 이 혼자 서는가" 다. 회원가입 화면은 그것만으로 쓸 수 있고,
`lib/services/student.ts` 는 부르는 화면이 있어야 의미가 있다 — 그런 것은
쓰는 화면과 함께 올린다.

**예외: 공통 코드는 단독으로 먼저 올린다**(§5-3).

### 2-2. 시작 전에 줄 것

```text
무엇을 만드는지          Screen ID 또는 기능 이름
어느 문서가 정하는지      COM-00X §Y
지금 어디까지 돼 있는지    관련 파일 경로
```

### 2-3. 끝났다고 말할 수 있는 조건

```text
tsc --noEmit      통과
eslint            통과
next build        통과
동작 확인          아래 §6
```

**넷 중 하나라도 안 했으면 "됐다" 고 하지 않는다.** 안 한 것은 안 했다고
말한다.

## 3. AI 에게 주는 규칙

### 3-1. 이름을 지어내지 않는다

Screen ID · 필드명 · 상태값은 **문서에 있는 것만** 쓴다. 비슷한 이름을
새로 만들면 집계할 때에야 드러난다 — `problem_complete` 와
`problem_completed` 가 섞이는 식이다.

### 3-2. 임의로 바꾸면 안 되는 영역

```text
COM-001 §19   AI 가 정답을 확신 못 하는데 임의로 정답을 만들지 않는다
              시스템 오류를 오답으로 평가하지 않는다
              Persona 가 정답 · 평가 · 난이도 · 검증을 바꾸지 않는다
              Student Memory 를 세션 종료 시 초기화하지 않는다
COM-002       다른 사람의 테이블명 · 필드명을 바꾸지 않는다
COM-003       Screen ID 와 화면명을 바꾸지 않는다
              State · Modal 을 별도 Route 로 만들지 않는다
COM-005 §14   스택을 바꾸거나 외부 서비스를 새로 들이지 않는다
```

### 3-3. 키를 프롬프트에 넣지 않는다

API Key · service_role 키를 대화에 붙여넣지 않는다. `.env.local` 만 쓰고
커밋하지 않는다(COM-005 §8).

## 4. 코드 리뷰 기준

### 4-1. PR 크기

**한 가지 일.** 줄 수로 못 박지 않는다 — 화면 하나가 300줄일 수도 있다.
대신 **제목이 "A 하고 B 도"** 가 되면 나눈다.

옮기기(refactor)와 고치기(fix)를 한 PR 에 섞지 않는다. 옮긴 것 안에 고친
것이 숨으면 리뷰가 불가능하다.

### 4-2. PR 본문에 반드시 적는 것

```text
왜        무엇이 문제였는지. 증상 그대로
무엇을     고친 방식과 그렇게 고른 이유
확인       어떻게 검증했는지 (숫자 · 로그 · 화면)
안 한 것   범위 밖으로 둔 것과 그 이유
```

**"안 한 것" 이 가장 중요하다.** 빠뜨린 것과 일부러 안 한 것은 다르고,
적어 두지 않으면 구분되지 않는다.

### 4-3. 승인

인원이 줄어 **PM 1명이 승인한다.** 스키마 변경(§8-2)과 공통 코드(§5-3)는
본인이 만든 것이라도 PR 본문에 근거를 남긴 뒤 merge 한다.

## 5. Git 규칙

### 5-1. 브랜치

```text
main        배포용
└─ develop  통합 지점
   └─ 작업 브랜치   develop 에서 따고 develop 으로 merge
```

이름은 `feat-` · `fix-` · `refactor-` · `docs-` · `chore-` 뒤에 무엇인지를
붙인다. `feat-mode-b` · `fix-signup-server-export` 처럼.

**develop 에 직접 커밋하지 않는다.** 한 번 그렇게 했고(2026-09-10) 브랜치를
따로 만들어 되돌렸다.

### 5-2. 커밋 메시지

```text
<타입>: <무엇을 했는지 한 줄>

왜 그렇게 했는지. 증상이 있었으면 증상 그대로.
판단이 있었으면 무엇과 무엇 사이에서 골랐는지.

검증: 무엇을 어떻게 확인했는지
```

타입은 `feat` · `fix` · `refactor` · `docs` · `chore`. 범위(`(dev)` 같은)는
붙여도 되고 안 붙여도 된다.

**한 줄 요약은 결과가 아니라 사실을 쓴다.** "버그 수정" 이 아니라
"가입하기를 누르면 500 이 나던 것".

### 5-3. 공통 코드는 단독으로 먼저

```text
package.json · types/database.ts · lib/constants/**
components/ui/** · supabase/migrations/**
```

기능 작업에 섞지 않는다. 섞으면 그 기능을 되돌릴 때 공통 코드까지 딸려
간다.

### 5-4. main

`develop` 을 merge 하는 것 외에 직접 커밋하지 않는다. main 에 올라가면
Vercel 이 프로덕션으로 배포한다.

## 6. 테스트 기준

### 6-1. MVP 에서 요구하는 것

**테스트 프레임워크를 도입하지 않는다.** 대신 아래를 지킨다.

```text
필수   tsc · eslint · next build
필수   바꾼 경로를 실제로 한 번 지나가 본다
       (화면이면 dev 서버, 서버 로직이면 노드 스크립트)
권장   판단이 들어간 순수 함수는 노드 단언으로 확인
```

`node --experimental-strip-types` 로 `.ts` 를 그대로 부를 수 있다.
`copy.ts`(58건) · 파이프라인 추출(31건)이 이 방식으로 확인됐다.

### 6-2. AI 응답처럼 매번 다른 것

**출력 내용을 단언하지 않는다.** 대신 형식과 규칙을 본다.

```text
확인할 것   JSON 으로 읽히는가
            필수 칸이 있는가 (verified_answer · completion.status …)
            보기가 4개인가
            **정답이 학생 문구에 섞여 있지 않은가**
확인 못 할 것  말투가 좋은가 · 문제가 적절한가
```

말투와 적절성은 사람이 눈으로 본다.

### 6-3. 배포 전 수동 확인

바꾼 화면을 실제로 연다. **버튼을 누른다** — 화면이 뜨는 것과 동작하는
것은 다르다. `'use server'` 파일에서 상수를 내보낸 실수는 빌드를 통과하고
버튼을 누를 때만 터졌다(2026-09-10).

## 7. 코드 스타일

### 7-1. 도구

```text
ESLint      next lint 기본 설정. 경고도 남기지 않는다
Prettier    도입하지 않는다. ESLint 로 충분하다
TypeScript  strict. any 를 쓰지 않는다
```

### 7-2. 주석

**무엇을 하는지가 아니라 왜 그렇게 했는지를 쓴다.** 코드를 읽으면 아는
것은 적지 않는다.

```text
안 좋음   // 학생 목록을 불러온다
좋음      // 계정 id 를 인자로 받지 않는다. RLS 가 이미 자기 계정 것만
          // 돌려주므로 여기서 또 거르면 같은 규칙이 두 곳에 생긴다
```

**되돌리면 안 되는 것에는 이유를 남긴다.** 순서가 중요한 코드, 일부러 안
한 처리, 한 번 겪은 함정.

### 7-3. 파일 길이

상한을 두지 않는다. 대신 **한 파일이 한 가지를 맡는다.** `PromptLab.tsx`
가 5,800줄인 것은 개발 도구라서 용인하고, 제품 코드에는 그런 파일을 만들지
않는다.

### 7-4. 이름

```text
폴더 · route     kebab-case
Component 파일   PascalCase
lib 파일         kebab-case
DB 컬럼 · 변수    snake_case (COM-002 §2)
Migration        YYYYMMDDHHMMSS_동사_대상.sql · 기존 파일 수정 금지
```

## 8. 금지사항

### 8-1. 학습 로직 (COM-001 §19 를 코드로)

```text
verified_answer 가 없으면 문제를 만들지 않는다
  → 지어낸 정답으로 학습을 이어가는 것이 가장 나쁘다

system_interrupted · verification_failed 는 집계에서 뺀다
  → 학생이 못 푼 게 아니다

needs_review 를 학생 화면에서 "실패" 로 쓰지 않는다
  → copy.ts 가 "한 번 더 도전" 으로 옮긴다

Persona 는 말투만 바꾼다
  → 프롬프트의 {{persona_block}} 을 치환하되 로직 분기에 쓰지 않는다

학생 화면에 내보내지 않는 값
  verified_answer(진행 중) · answer_lock · evaluation · logic_gap
  ai_wrong_answer · ai_wrong_reasoning · target_misconception
```

### 8-2. 스키마

**DB 를 먼저 바꾸지 않는다.** 필드가 없으면 COM-002 에 변경 제안을 쓰고
승인을 받는다. 제안에는 **없으면 무슨 일이 생기는지**를 적는다.

마이그레이션은 추가만 한다. 기존 파일을 고치지 않는다.

### 8-3. 검토 없이 merge 하지 않는다

AI 가 쓴 코드도 사람이 PR 을 읽고 merge 한다. 자동으로 merge 되게 두지
않는다.
